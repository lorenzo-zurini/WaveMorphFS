# Contributing

Thanks for helping. WaveMorphFS serves people's music libraries, so correctness
comes first: generated files must be exact, and source files must never change.

## Building and testing

```sh
cmake -S . -B build -G Ninja -DWAVEMORPH_WERROR=ON
cmake --build build
build/wavemorphfs-tests            # all tests; or a name filter: build/wavemorphfs-tests wavpack
```

The tests need the `flac`/`metaflac` and `ffmpeg` command-line tools. Before
sending a change, also run the suite under the sanitizers:

```sh
cmake -S . -B build-asan -G Ninja -DCMAKE_BUILD_TYPE=Debug -DWAVEMORPH_SANITIZE=address,undefined
cmake --build build-asan && build-asan/wavemorphfs-tests
```

## Rules the code keeps

1. **Source files are never written.** Everything a user changes goes into
   sidecars (`wavemorph.json`).
2. **Audio is never cached.** Only positions, sizes and checksums are; audio is
   always read (or decoded and encoded) from the source when it is read.
3. **Tag names are kept as found.** Names match case-insensitively and synonyms
   count as one field, but the spelling given is the spelling written.
4. **Output is exact.** File sizes are known before any byte is produced, and
   audio is sample-identical to the source. Changes that touch generated bytes
   are checked against reference tools (`flac -t`, `wvunpack -v`, FFmpeg) and
   byte-compared against the previous version on a real library.
5. **Changed output moves the output epoch** (`OUTPUT_EPOCH_NS` in
   `src/library.cpp`), so music servers re-read the files.

## Style

- C++20, the style of the surrounding code (4-space indent, about 150 columns).
- Every source file starts with `// SPDX-License-Identifier: GPL-3.0-or-later`.
- Comments explain why, not what. Errors go through `fail(...)`,
  `WM_ENSURE(...)` and `with_context(...)`.
- Zero compiler warnings.
- Commit messages: a summary line, then a body explaining the change and why.

## Checking a change on a real library

`wavemorphfs --root NAME=PATH ls <dir>` shows what a folder looks like through
the filesystem; `verify <dir>` checks every generated track with the reference
decoders; `compare <dir> <split dir>` compares tracks with already-split files.
For changes to generated output, mount the new build next to the old one (with
copies of the tags and cache directories) and compare whole files and random
reads between the two mounts.
